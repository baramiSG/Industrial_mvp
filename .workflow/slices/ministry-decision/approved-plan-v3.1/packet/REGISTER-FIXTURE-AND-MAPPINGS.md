# Finite register fixture and mapping supplement — v3.1

Normative proposed detail for the two v3 contracts. All values below are **authored Class-D demonstration parameters**, pending the reviewed owner parameter ruling; they are not extracted Ministry records. This supplement closes field/operator choices so Cascade need not invent a technical ontology. Actual runtime JSON and ground-truth tests are implementation outputs under this specification, not written in this planning task.

## 1. Record kind and selector closure

The `fact.kind` discriminator admits only the following record payloads. `fact.dataset_kind` is REGISTRY, PRODUCTION_ACTUALS, FACTORY_CUSTOMS, APPLICATION_TAPE or TECHNICAL_ENRICHMENT. A record at company scope is not a factory record. Record fields are homogeneous in origin; split mixed-origin assertions. Unknown values are null; mandatory identity/enums cannot be null. All pointer/type/window validators in the companion contracts apply.

| kind | Closed `values` keys / admitted selector fields |
|---|---|
| REGISTRY_ACTIVITY | `country,status,product_family,process_route,operating_status_asserted_by_registry` |
| PRODUCTION_ACTUAL | `hs_revision,hs6,production_kind,process_family,quantity_kt` |
| FACTORY_CUSTOMS | `hs_revision,hs6,description,flow,quantity_kt,reexport,transaction_id,equipment_model_id` (last two nullable; required only by P04) |
| EQUIPMENT_TECHNICAL | `customs_fact_id,transaction_id,equipment_model_id,function,workpiece_material` (optional, TECHNICAL_ENRICHMENT dataset; equipment function, not installed-line state) |
| APPLICATION | `stage,reason_code,proposed_activity,proposed_capacity_kt,proposed_start_month` |
| TECHNICAL_FIELD | `field_id,value,unit,requirement_id` |
| CAPACITY | the six exact legacy names: `nameplate_kt,availability,yield,qualification_share,market_allocation_share,current_utilisation` |
| QUALIFICATION | `requirement_id,application,customer_status,valid_window_months` |
| WINDOW | `available_window_months` |
| EFFORT | exactly the nine configured dimension keys |
| ALLOCATION | `qualified_available_kt,requirement_id,window_months` |
| CEILING | `group_id,ceiling_kind,value_kt,basis` |
| CERTIFICATE | `certificate_kind,scope,valid_window_months` |

The allowed `(record_kind,value_field)` selectors are **only the pairs in this table**, restricted further by the rule table below; FACTORY_CUSTOMS.description is a stored display field and explicitly excluded from selector admission. No dotted arbitrary expression/path evaluator is introduced. TECHNICAL_FIELD.field_id is restricted to DOMAIN's fixed technical comparator fields; its value/unit type is dictated by that field. EQUIPMENT_TECHNICAL's separate function/material fields serve P04 only, never the installed-line technical comparator. Source references point to exact original fields; display text never drives matching.

`status` is OPERATING or UNDER_ESTABLISHMENT; `operating_status_asserted_by_registry` is an explicit Boolean registry assertion, not inferred from the existence of a licence. It fills only the simulated R9-S prerequisite under the unchanged rule; it is not verification of a real plant. Use “Registry asserts operating · Class D” / «يفيد السجل بأن المصنع يعمل · الفئة د». `production_kind` is OWN_PRODUCTION or AGGREGATE; only OWN_PRODUCTION with explicit plant scope may serve per-plant production evidence. `flow` is IMPORT or EXPORT and reexport is Boolean. `stage` is APPLIED, REJECTED or APPROVED; all describe the application, never installed state. `description` is nullable human-readable source text only: it is never a selector, lookup key, equipment class, fallback or reason to override HS identity. Reject legacy `description_tag` and authored `equipment_class` matching inputs. P04 computes its class from the admitted code and independently sourced technical fields below; renaming an old tag cannot supply that basis.

Coverage entries identify full supplied extract scope/window, not national completeness. Registry as-of2026-06-30; production calendar2024; customs calendar2025; application extract2026-06-30; technical enrichment as-of2026-09-12 with relative-month windows anchored there. Retain historical wording on production/customs. No silent carry-forward to current technical qualification. Missing dataset vs searched empty scope are separate outputs. Add/delete rows in mutation tests also updates declared coverage scope where required; this is a record change, not a candidate whitelist.

These are finite Class-D requirement parameters; no standalone config or process catalogue is created. Existing target numeric/specification leaves remain pointers. Adding any other item or meaning requires review.

**HS identity and parameter storage.** New customs rows use `hs_revision="H6"` (HS2022) and `hs6` as an exact six-digit string. The legacy request's H0 product identity stays unchanged; it does not supply or overwrite the transaction's revision. Each applicable `requirement_items[]` entry keeps its existing keys and `record_selectors` pairs; its `required_value_ref` resolves an item-keyed entry in the already-admitted `requirements_additions.discovery_items`. For P03/P04 each such entry has exactly `{item_id,rule_id,record_selectors,hs_revision,admitted_hs6,basis}`; `admitted_hs6` is the finite list in the table, `basis` identifies the nomenclature edition/source and the Class-D target rationale. These target parameters inherit ENGINEERING_DECLARATION origin, separate from the customs record and P03/P04 inference; no additional item key is introduced. Both copies' validation checks exact agreement between item, selector, code list and the frozen P03/P04 table. No standalone config, inferred crosswalk or product-family change.

A heading such as **7901, 8455, 8417, 8514, 8479 or 8477 has four digits**; it cannot appear in an `hs6` field/set. A two-digit chapter84/85 is still broader. Do not pad, truncate, prefix-match or expand a heading into unspecified children. A valid transaction code in another revision does not match H6 without a separately reviewed concordance; return NOT_ESTABLISHED with the identity/concordance request, not ABSENT. Missing/invalid six-digit identity fails the strict record validator; a valid non-admitted code is a non-match, not a malformed record. Procurement findings use recorded IMPORT/non-re-export facts and covered window, not description, value or unit price.

**Sourced equipment classification (P04, optional).** The raw customs fact remains DIRECT_RECORD. Its `transaction_id` and `equipment_model_id` are exact source fields when supplied, null otherwise. An EQUIPMENT_TECHNICAL fact is an explicitly sourced ENGINEERING_DECLARATION with the same subject and exact `customs_fact_id`, transaction and model identifiers. Its declared validity must cover the referenced acquisition period; a later source date is permitted only when it explicitly describes that transaction/model at acquisition. Keep source date separate from the covered period, using the existing window convention; neither establishes current installation. `function` is HOT_DIP_ZINC_COATING, EXTRUSION, WIRE_COIL_WINDING or OTHER; `workpiece_material` is STEEL_STRIP, PLASTICS or OTHER. Its `source_refs` must resolve the supplied technical declaration's exact transaction/model/function/material fields and source identity; the fixture is authored and reviewed as Class D, never portrayed as an actual supplier confirmation. All fields share that declaration origin. A free description, unsourced class label, invoice number alone or another model's brochure cannot substitute. No automatic prose extraction is proposed.

Equipment class is a derived P04 meaning, **not a new finding key**. Preserve the exact code/function/material operands in existing `current_recorded`; encode the two admitted classifications in existing `reason_code` as `P04_GALVANISING_ACQUISITION` or `P04_PLASTICS_WORKING_CONTEXT`, with `origin=REVIEWED_INFERENCE`, `rule_id=P04` and refs to both facts and exact operands. Never accept an authored `equipment_class` matching input or assign inference origin to the raw customs fields. The two closed cases are: H6/847981 + linked HOT_DIP_ZINC_COATING/STEEL_STRIP → GALVANISING_EQUIPMENT acquisition; H6/847720 + linked EXTRUSION/PLASTICS → PLASTICS_WORKING context. Any missing/unsupported basis yields NOT_ESTABLISHED and a specific model/function-source request; conflicting operands yield CONFLICTED. An invalid foreign/dangling link fails closed. No classification grants installation, operating process, envelope, qualified capacity, engineering state, K or route permission.

This narrows Claude's illustrative machinery headings deliberately: 847981 covers other metal treatment too, so a wire coil-winder is a negative control; 847720 is plastics-working extrusion, not evidence of PP resin polymerisation. Other 8455/8417/8514/8479/8477 children are not implicitly admitted. This is a finite demonstration rule, not general machinery classification. Equipment enrichment remains optional and the no-enrichment path is unchanged.

**Attribution:** apply valid-code procurement/equipment context at the company's recorded grain even when no factory link exists. Promote an admitted signal to a named plant's R9-S adapter only through the existing explicit, dated fact→plant attribution with valid allocation/window and ownership. It supplies no line fact absent separate line attribution. Two plants cannot share a company-level transaction by fan-out; moving a row from plant to company scope changes the plant finding and its next attribution request, not the existence of the company's record.

Primary nomenclature grounding (read for this revision): [Japan Customs HS2022 Chapter79](https://www.customs.go.jp/english/tariff/2022_1_1/data/e_79.htm) identifies 790111/790112 as non-alloyed unwrought zinc subheadings; those classification bands are not measured batch purity. [Japan Customs HS2022 Chapter29](https://www.customs.go.jp/english/tariff/2022_1_1/data/e_29.htm) identifies 290122 as propene/propylene. [Japan Customs HS2022 Chapter84](https://www.customs.go.jp/english/tariff/2022_1_1/data/e_84.htm) identifies 847981's metal-treatment scope including coil-winders and 847720 extruders. These sources support nomenclature only; the target-specific process relevance and technical records remain proposed P1 demonstration parameters. No Saudi national tariff suffix or actual Ministry record classification is asserted.

Process enum is HOT_DIP_GALVANISING, COLD_ROLLING, RESIN_PRODUCTION or OTHER. RELATED_ONLY cold-rolled relationship is a **declared demonstration target relationship** for this steel requirement, not an amendment to the general product_families membership. New unrelated process taxonomy/HS equipment inference is excluded. A target mutation between steel and PP selects its own items and changes relevant companies without editing register contents.

R9-S receives only its existing six signal types. The admitted subset here is core_process from an independent explicit process assertion, adjacent_output, imported_inputs, equipment or relevant_certification; matching_feedstock is unused rather than inferred from chemical procurement. The same factual assertion cannot satisfy the operating/family prerequisite and the only additional signal; duplicated/pair-labeled customs records do not inflate counts. Unknown gates allow only the coarse screen; a known failure blocks exactly the evaluated scope. Factory PASS_TO_ASSESSMENT is never “this line meets the target.”

## 4. Allocation, reference alias and comparator closure

Each line entry adds exactly `availability_basis:FORMULA|DECLARED_ALLOCATION` and `allocation_ref:fact_id|null` to the reference-only schema. FORMULA requires null allocation_ref; DECLARED_ALLOCATION requires a same-line/same-requirement/window ALLOCATION fact. Validate finite nonnegative allocation≤formula-qualified capacity **for new candidates only**. Preserve existing aggregate/other-sector exceptions. No missing-factor call to effective_qualified_capacity; arithmetic output is null until operands exist.

Return `formula_capacity_kt`, `admitted_qualified_supply_kt`, `allocation_basis`, `capacity_result`, `window_result` separately. Complete arithmetic is not admitted qualified supply when a critical current technical/qualification fact is unknown/conflicted. Inconsistent positive qualified-share/allocation alongside a current hard mismatch emits CONFLICTED and withholds admitted supply; do not cap it silently. Explicit NOT_QUALIFIED with0share/0allocation supports a known0 quantity and known qualification failure.
